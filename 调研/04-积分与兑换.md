# 积分体系 / 奖励商城 / 奖品兑换 设计调研（供 PRD 使用）

> 覆盖 Habitica/Forest/Duolingo、ClassDojo/班级优化大师/小红花、电商会员积分与 Kickstarter 奖励档位。案例来自官方帮助与公开报道，工程结论来自积分账本、库存扣减实践。

## 一、五条结论

1. **积分是负债，兑换是订单**：账户、流水、冻结、对账四件套缺一不可，余额只是流水的投影。
2. **奖品分三层**：`reward_item`（内容）+ `reward_offer`（积分价/库存/限购/人群/时间）+ `redemption`（订单+快照）。
3. **状态机不要一个大枚举**：主状态、履约状态、退款状态分开；“已通过”与“待发放”可合并。
4. **防超卖靠数据库原子条件更新**，不是“先查后扣”；限购也要原子计数。
5. **防通胀靠发行上限、真实消耗、过期与负债看板**，不是临时提高兑换门槛。

## 三、奖品数据模型

| 分组 | 字段 | 规则 |
|---|---|---|
| 基础 | `id`、`scope_type/scope_id`、`code`、`name`、`subtitle`、`category_id`、`tags[]`、`rarity`、`status` | scope 区分平台/企业/班级/家庭；rarity 仅展示 |
| 内容 | `description`、`cover_image_id`、`gallery_image_ids[]`、`alt_text`、`terms`、`supplier` | 多图有序；terms 写清退换、有效期、运费 |
| 价格 | `points_price`、`original_points_price`、`cash_price`、`currency_type` | 积分为整数；支持积分+现金；币种与账户 scope 一致 |
| 库存 | `stock_total/available/reserved/sold`、`unlimited_stock`、`max_per_order` | `available=total-reserved-sold`；调库存不得低于 reserved |
| 限购 | `per_user_limit`、`per_period_limit`、`period_type`、`cooldown_hours` | 总量+周期+冷却三层 |
| 时间 | `online_at`、`offline_at`、`redeemable_from/to`、`valid_days_after_redeem` | 上架时间与可兑换时间分开；虚拟凭证另有有效期 |
| 履约 | `fulfillment_type`、`requires_address`、`shipping_template_id`、`pickup_location`、`code_policy`、`auto_complete_days` | 虚拟码/链接、实物配送、线下自提、人工发放、权益类 |
| 审核/可见 | `requires_approval`、`visibility`、`audience_rule`、`access_code` | public/unlisted/segment；audience_rule 存 JSON |
| 运营/审计 | `pinned`、`sort_weight`、`featured_until`、`version`、`created_by`、`published_at`、`archived_at` | 置顶与排序分离；version 用于快照/并发 |

**拆 `reward_item` 与 `reward_offer`**：同一奖品可有不同规格、早鸟价、人群价，各自有库存、限购、时间窗；MVP 可合并，但订单必须保留 `offer_id`。订单字段至少含：`order_no`、`user_id`、`offer_id`、`reward_snapshot`、`quantity`、`points_price`、`points_frozen`、`status`、`fulfillment_status`、`refund_status`、`address_snapshot`、`code_id`、`tracking_no`、`pickup_location`、`approver_id`、`approved_at`、`completed_at`、`version`。另设 `redemption_event`（from/to/actor/reason/time）、`reward_user_quota`（user_id、offer_id、used_count、reserved_count、last_redeemed_at）。

## 四、兑换流程与状态机

**主流程**：详情页读 offer 与可兑额度 → 提交（带幂等键）→ 校验上架/时间/人群/限购/库存/积分 → 同一事务冻结积分、预占库存与限购、写订单/快照/流水/事件 → 可选审核 → 待发放 → 发放中 → 已发放 → 已完成。取消/拒绝解冻退分、释放库存；售后则退款退分、按规则回库。

| 状态 | 含义 | 说明 |
|---|---|---|
| `PENDING_REVIEW` | 待审核 | 仅需审核时进入；积分冻结、库存预占 |
| `PENDING_FULFILLMENT` | 待发放（已通过） | 审核通过或自动通过；UI 可显示“已通过，待发放” |
| `FULFILLING` | 发放中 | 备货、生成兑换码、安排自提 |
| `FULFILLED` | 已发放 | 已发货/已发码/已备货待取 |
| `COMPLETED` | 已完成 | 确认收货或到期自动确认；进入售后窗口 |
| `REJECTED` | 已拒绝 | 审核不通过；终态 |
| `CANCELLED` | 已取消 | 履约前取消；终态 |
| `REFUNDED` | 已退款/退回积分 | `refund_status` 区分 full/partial；终态 |
| `FAILED` | 发放失败 | 可重试，也可转退款 |
| `CLOSED` | 已关闭 | 凭证过期/放弃领取/完成后归档；终态 |

| # | 当前 → 事件 → 下一状态 | 副作用/校验 |
|---|---|---|
| 1 | — → 提交兑换 → 待审核/待发放 | 冻结积分、预占库存与限购、写快照；幂等键唯一 |
| 2 | 待审核 → 审核通过 → 待发放 | 记录审核人/时间；通知 |
| 3 | 待审核 → 审核拒绝 → 已拒绝 | 解冻退分、释放库存/限购；填原因 |
| 4 | 待审核/待发放 → 用户取消 → 已取消 | 同上；已进入发放中不允许直接取消 |
| 5 | 待发放 → 开始履约 → 发放中 | 分配履约人；生成码/拣货单 |
| 6 | 发放中 → 发货/发码/备货完成 → 已发放 | 冻结转实扣、reserved 转 sold、写 tracking/code |
| 7 | 已发放 → 确认收货/自动确认 → 已完成 | 启动 7–15 天售后计时 |
| 8 | 发放中 → 发放失败 → 发放失败 | 保留冻结/库存；记录原因，可重试 |
| 9 | 发放失败 → 重试 → 发放中 | 新履约任务；不得重复扣分 |
| 10 | 已发放/已完成 → 售后退款 → 已退款 | 退分；实物验收后回库；虚拟码作废 |
| 11 | 已发放 → 凭证过期/未领取 → 已关闭 | 默认不退；terms 提前写明 |
| 12 | 已完成/已退款/已拒绝/已取消 → 归档 → 已关闭 | 只读；不再迁移 |
| 13 | 待审核 → 超时未审 → 已取消 | 自动退分；配置 SLA |
| 14 | 待发放 → 超时未履约 → 已取消 | 商家无法履约时全额退分 |

**不变量**：每次迁移写 `redemption_event` 与账本流水；`version` 乐观锁防并发重复迁移；退款/释放库存必须幂等且只执行一次；`COMPLETED` 后只能走售后，不能回待发放。

## 五、关键边界

| 场景 | 规则与处理 |
|---|---|
| **重复兑换** | `per_user_limit`（总次数）+ `per_period_limit`（日/周/月/学期）+ `cooldown_hours`（冷却）。`reward_user_quota` 原子占额度；取消/拒绝释放，已发放不释放。前端置灰只是体验，服务端必须再校验。 |
| **并发超卖** | `UPDATE reward_offer SET stock_available=stock_available-1, stock_reserved=stock_reserved+1 WHERE id=? AND stock_available>=1`；影响行数 0 即售罄。积分同理：`UPDATE point_account SET balance=balance-?, frozen=frozen+? WHERE id=? AND balance>=?`。两条更新+订单+流水+额度在同一事务，任一步失败全部回滚。不要“先 SELECT 再 UPDATE”。 |
| **重复提交** | 客户端生成 `idempotency_key`；唯一键 `(user_id, offer_id, idempotency_key)`；重试返回原订单，不重复扣分/占库存。 |
| **积分不足/正好相等** | `<` 返回 `INSUFFICIENT_POINTS` 并显示差额，不创建订单；`==` 允许，余额归零，二次确认；不允许多扣成负数。 |
| **库存为 0** | 返回 `OUT_OF_STOCK`，按钮置灰；可登记到货提醒，但不生成订单。页面价格/状态已变化时返回 `PRICE_CHANGED`/`OFFLINE`，让用户确认新价，不静默成交。 |
| **取消/拒绝退分** | 履约前全额退；已履约走售后。默认只做全额退；部分退仅用于“组合包且子项单独定价”，按快照分摊，MVP 不建议做。退款积分建议发新批次、有效期 90 天；若按原批次过期则可能“退了等于没退”，须在条款写明。 |
| **下架/归档后的历史订单** | 订单详情永远读 `reward_snapshot`；下架只影响新兑换，不影响已产生的凭证/发货/自提；归档不能删订单、码、流水。 |
| **奖品编辑** | 首次兑换前可自由改；首次兑换后锁定积分价、履约类型、限购；库存只可追加；描述/图片可改但历史订单用快照。必须改价时新建 `offer` 版本。Kickstarter 的“有支持者后不可改，只能加库存/国家”可直接作为规则边界。 |
| **积分过期/清零** | `point_lot` 按获取时间 FIFO 扣减；每日任务写 `EXPIRE` 流水，不允许负余额。建议滚动 24 个月（或次年年底），提前 30/7/1 天提醒，避免突然清零。班级积分按学期结算时，应做“结转/清零”公告与存档，而不是静默过期。 |

## 六、管理后台 / 归档 / 图片

**后台必备**：奖品 CRUD、草稿/定时上架、复制、分类标签、多图排序、条款、审核开关、可见人群、置顶排序；库存增减（填原因）、库存流水、低库存预警、售罄自动下架；订单按状态/时间/奖品/用户/履约方式筛选，详情含快照、事件时间线、地址、码、物流；批量审核、批量发货（导入物流单号）、批量生成/导出兑换码、打印拣货单、自提核销、重发通知；取消/拒绝/退款/退分/作废码/回库；操作日志（前后值、操作人、IP、原因）、黑名单、限购豁免、异常告警；看板含发放/消耗/过期/结余、兑换率、售罄率、热门奖品、审批/履约时效、退款率、对账差异、刷分告警。核心指标是**积分负债**：`结余 × 单积分成本 × 预计兑付率`。

| 归档方式 | 语义 | 可恢复 | 前台搜索 | 历史订单 | 适用 |
|---|---|---|---|---|---|
| **软删除** | `deleted_at`，记录还在 | 可 | 不展示 | 不保证可打开 | 草稿、重复创建、误建 |
| **归档** | `status=ARCHIVED`，业务退役 | 可 | 不搜索/不展示；订单详情可看 | 完整保留 | 已发布过的奖品 |
| **硬删除** | 物理删除 | 不可 | 不展示 | 断链 | 仅无引用且过保留期的草稿 |

规则：**发布过的奖品永不硬删，只归档**；归档后不能新兑换，但已产生的兑换继续履约；公开搜索固定 `status=ACTIVE AND now BETWEEN online_at AND offline_at`，后台可 `include_archived=true`；订单/流水/码至少保留 3 年，到期脱敏而非直接删。归档不是删除，UI 要分开，避免运营误操作。

**图片**：JPG/PNG/WebP，单张 ≤5MB；封面 1:1（1200×1200），详情 3:2（1200×800），最多 5 张，禁 SVG。链路：前端裁剪/排序 → 直传对象存储（STS 临时凭证）→ 服务端校验 MIME+文件头 → 重编码 WebP/AVIF → 去 EXIF → 随机文件名 → 病毒扫描/图片审核 → 写 `image_asset`。`cover_image_id` 与 `gallery[]` 分开，`sort_order` 支持拖拽，每张有 `alt_text`。对象存储+CDN；公开图长缓存+版本化 URL，私密图签名 URL；Referer 白名单/时间戳 token；禁止目录列举。机审（涉黄/暴恐/二维码/联系方式）+ 人审兜底；快照引用不可变 URL，避免换图导致旧订单图裂。参考 [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) 与 [Cloudinary](https://cloudinary.com/documentation/image_transformations)。

## 七、积分账本

**为什么用流水**：余额可直接改，但并发、退款、过期、客诉叠加后无法还原“为什么变成这个数”。流水是事实源，余额是物化视图；对不上账时可重放。腾讯云实践总结为“账户→流水→冻结→对账”四层，强调条件更新、幂等键、每日对账（[文章](https://cloud.tencent.cn/developer/article/2748310)）。

**字段**：`id`、`account_id`、`biz_type`（签到/任务/兑换/退款/过期/调整）、`biz_id`、`idempotency_key`、`delta`、`frozen_delta`、`balance_before`、`balance_after`、`lot_id`、`expires_at`、`operator_id`、`reason`、`reversal_of`、`created_at`。

**规则**：只追加，不更新/删除；退款用反向分录并关联原流水；唯一键 `(account_id, idempotency_key)` 与 `(account_id, biz_type, biz_id)` 防重；每日对账 `SUM(delta)=balance`、`SUM(未结冻结)=frozen`；差异只告警、不自动改账。原流水已消耗时，追回不能扣成负数，应限制后续获取或走人工债务处理。

## 八、对我方产品的可借鉴建议

**定位**：签到/计时是“发行端”，奖励商城是“回收端”。发行端不设上限，商城再花哨也会通胀；回收端没有真实成本，积分就会变成游戏币。

**MVP 优先级**：

1. **一个 scope 一种积分**：个人、班级、家庭、企业各自独立账户；不要把班级积分和家庭星星混在一个余额。ClassDojo 已证明“同一分两边都能兑”会重复兑付。
2. **表结构先立住**：`point_account`、`point_ledger`、`point_lot`、`reward_item`、`reward_offer`、`redemption`、`redemption_event`、`redemption_code`、`reward_user_quota`、`stock_log`。UI 可少做，字段先留。
3. **兑换走“冻结→实扣”**：下单冻结积分与库存，发放时实扣，取消/拒绝解冻；比“下单即扣、退款再补”更不容易出现负余额和重复退。
4. **低额自动通过，高额/实物人工审核**；审核要有 SLA，避免“待审核”变成永久状态。
5. **后台先做订单列表、批量发货、退款、日志、对账**，再做装修。运营每天用的是筛选、导出、批量操作。

**避免积分通胀**：

- **发行上限**：签到、计时、任务、活动分别设日/月上限；发放量增速不超过业务增速的 1.2–1.8 倍；每月做发行预算。
- **只奖励被验证的行为**：签到按连续天数递减/封顶，计时按有效时长，任务按质量；不为“打开 App”“重复点击”发分。
- **真实消耗**：实物、限量、积分+现金、公益、外观/勋章、连续冻结等；行业分析常用“消耗率 45%–65%、通胀率 <8%–10%、沉默积分 <30%”作预警（[行业分析](https://www.eshutong.com/archives/88175.html)，需按业务校准）。
- **过期与 FIFO**：滚动 24 个月+提前提醒+按获取时间扣减；腾讯视频的“次年年底过期、FIFO、每月上限 1 万”可落地（[规则](https://film.video.qq.com/x/credit_mall/route/faq)）。
- **价格锚**：固定“100 积分 ≈ ¥1”心智；调价用新 `offer` 版本，不追溯老订单；不要突然把 500 分改成 5000 分。
- **稀缺性**：限量库存、每人限兑、限时上架、等级专属；不要伪造库存/倒计时。

**避免刷分**：

- **幂等+限频+设备/IP/行为风控**：签到、分享、邀请按用户/设备/IP 限频；异常密度进人工复核（[实践](https://cloud.tencent.com.cn/developer/article/2554978)）。
- **延迟到账**：任务积分 T+7 解冻，确认无退款/无作弊后再可用；高价值兑换要求手机号/实名校验。
- **追回与黑名单**：协议写明“作弊可撤销积分、冻结账户、追回已兑权益”；腾讯视频即取消违规积分、中止账号、追回福利（[规则](https://film.video.qq.com/x/credit_mall/route/faq)）。
- **兑换侧**：同一地址/设备每月兑换次数上限、虚拟码一次性核销、禁止积分转让/售卖、实物签收留痕。

**MVP 不做**：多币种、复杂组合包、部分退款、动态定价、双向积分转账。等单币种跑通、账本对平后再加。

**验收**：超卖 0、账实差异 0、兑换成功率 >99%、审核 <24h、发货 <48h、退款 <3 个工作日、刷分损失 <0.5%、通胀率 <10%。
