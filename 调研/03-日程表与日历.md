# 日程表 / 待办 / 日历 产品调研（供 PRD 使用）

> 覆盖 TickTick、Notion/Obsidian 模板、Google/Outlook、Sunsama/Motion/Reclaim、Structured/Things 3/Todoist、Clockify。资料来自官方文档与 2026 年 9–10 月测评。

## 一、四条结论

1. 事件与任务应**统一建模、分类型呈现**：一张 Entry 表 + `kind`，不要两套日历两套提醒。
2. 重复规则的门槛不在"能不能每天"，而在**例外怎么处理**（跳过这次 / 只改这次 / 改此后全部）。
3. 习惯进日历应是**"建议时段块"而非"承诺事件"**，错过不惩罚才符合养成逻辑。
4. 计时器是日程与统计之间唯一的事实源；没有"预估 vs 实际"，统计只是好看的数字。

## 二、事件与任务：字段差在哪，要不要都做

| 维度 | 事件 | 任务 |
|---|---|---|
| 时间 | 占用一段真实时间，可全天/跨天 | 截止或计划做，可无时间 |
| 状态 | 无"完成"，只有发生/取消 | todo / done / cancelled + completedAt |
| 重复 | 规则生成实例，实例可单独改删 | 完成后生成下一次 |
| 参与者 | 组织者、RSVP、忙闲 | 通常无 |
| 提醒 | 相对开始/结束 | 相对截止，常带逾期升级 |
| 统计 | 占用时长 | 预估 vs 实际 |

RFC 5545 本就把 `VEVENT` 与 `VTODO` 分为两个组件，VTODO 独有 `DUE`、`COMPLETED`、`PERCENT-COMPLETE`、`STATUS`（[RFC 5545](https://datatracker.ietf.org/doc/html/rfc5545)）。所以**该同时支持**，但不必做两套 UI。Reclaim 把条目分为 Habit（重复、柔性、无截止）、Task（一次性、有截止、按预估工时排）、Focus Time（重复、无具体任务）（[Reclaim](https://help.reclaim.ai/en/articles/11325700-habits-vs-tasks-vs-focus-time-when-to-use-each-in-reclaim)），本质是按"承诺强度"分类，可直接借鉴。三种产品代表了三种取舍：Things 的 Today 只做"待办 + 只读日历"两层（[官方](https://culturedcode.com/things/support/articles/2803583/)），Structured 把两者压成一条时间轴（[官网](https://structured.app/)），Todoist 则把日历视图与任务时长做成付费能力（[对比](https://toolradar.com/compare/structured-vs-todoist)）。

## 三、日历视图

| 视图 | 用途 | 必备交互 |
|---|---|---|
| 今日/议程 | 移动端默认，回答"现在做什么" | 当前时间线、一键计时 |
| 日/时间轴 | 执行日计划 | 拖动改期、拉伸改时长、重叠并排 |
| 周 | 排下周、看负荷 | 跨天条、拖到另一天 |
| 月 | 找空档 | 点日期下钻，不做精细编辑 |
| 多日历 | 工作/个人/订阅 | 颜色 + 显隐，订阅源只读 |

TickTick 有年/月/周/议程/多日/多周六种视图，时间线可拖拽改开始时间与时长（[TickTick](https://ticktick.com/features)）；Clockify 日历可缩放到 5 分钟、拖动/拉伸/拆分，并要求避免重叠（[Clockify](https://clockify.me/help/track-time-and-expenses/calendar-view)）。**移动端别照搬桌面**：窄屏拖拽误触高，用"长按 → 改期"更稳。TimeBlocks 一类"日历 + 待办 + 便签"三合一的移动应用，本质也是把一切条目塞进同一条时间轴。

## 四、RRULE 支持到什么程度

RRULE 由 `FREQ`、`INTERVAL`、`BYDAY`（可带序数 `3TU`/`-1FR`）、`BYMONTHDAY`、`BYSETPOS`、`COUNT`/`UNTIL` 组合；单个实例用 `EXDATE` 排除、`RECURRENCE-ID` 改期，`RANGE=THISANDFUTURE` 改此后全部（[RFC 5545](https://datatracker.ietf.org/doc/html/rfc5545)）。

- **L0 必须**：每天、每周固定几天、每 N 天/周、每月某日、每年；结束条件（永不/某日/共 N 次）。
- **L1 应有**：每月第 N 个周几（含"最后一个周五"）；单次跳过与单次改期。
- **L2 可延后**：多 RRULE 合并、RDATE 加实例、THISANDFUTURE、复杂 BYSETPOS。

常用前 5（经验判断）：每天、每周固定几天、工作日、每 N 周、每月同日。「每年」排第 6，「每月第 N 个周几」虽低频却是月度复盘刚需。

两个工程事实：Google Calendar API 用"母事件 + 例外实例"表达重复（`recurringEventId`/`originalStartTime`，删除的例外为 cancelled），展开需 `singleEvents`（[Google API](https://developers.google.com/workspace/calendar/api/guides/recurringevents)）；Outlook 只实现 RFC 子集，不支持任意 RDATE 新增实例，会把 RDATE/EXDATE 配对当作"移动过的实例"（[MS-STANOICAL](https://learn.microsoft.com/en-us/openspecs/exchange_standards/ms-stanoical/441e3a4a-e25f-45d3-b93b-d6045eccef0e)）。"支持 RRULE"要区分"UI 能设"和"能无损导入导出"。

## 五、提醒

- **提前量给三档**（准时/提前 10 分钟/提前 1 小时），别甩一个 0–10080 分钟输入框。
- **多提醒**：TickTick 支持多个提醒时间、结束时间提醒、持续响铃（[TickTick](https://ticktick.com/features)）；MVP 给 2 个够用。
- **全天事件**没有开始时刻，提醒挂在"当天 09:00"，并支持"前一天 20:00"——最常被漏。
- **错过提醒**：本地通知在关机/免打扰/切时区时不可靠，应在下次打开时给一条"错过汇总"。
- 相对开始的提醒必须随改期重算；`UNTIL` 过期、`COUNT` 用尽后停止调度。

## 六、与习惯打卡整合

三条路线：① 习惯 = 日历块，如 Reclaim 的 Habit 在偏好时间窗内自动找位；② 习惯 = 待办，完成后写打卡记录；③ 提醒 + 冲突检测。

推荐**时间窗柔性块**："希望 07:00–09:00 之间完成 30 分钟"。硬事件错过即挫败，柔性块允许"今天晚点做"。TickTick 把习惯、番茄、四象限做成与日历并列的模块，习惯有独立统计（[TickTick](https://ticktick.com/features)），说明**习惯不必都塞进日历**，日历只回答"今天打算何时做"。冲突检测应"提示不阻断"：标黄 + 建议顺延，不禁止保存。

### 模板派的做法（Notion / Obsidian）

Notion 的习惯模板通常是"习惯 × 日期"的数据库，time blocking 是另一张按日分组的表，靠 database templates 复用每日页面（[Notion](https://www.notion.com/help/database-templates)）；Obsidian 以 Daily note 为容器，配社区日历/任务插件把当天时间块写成纯文本（[插件](https://obsidian.md/plugins)）。优点是自由、数据归自己；代价是无提醒、无冲突检测、录入成本高、移动端弱——恰好反证了"轻"的价值。

## 七、与计时器整合

链路：块/任务 → 一键计时（带出标题、技能、预估）→ 结束问"完成了吗" → 标记 + 写实际时长 + 发积分。字段：`estimateMin`、`actualMin`（可累加）、`sessions[]`、`source`。

Sunsama 把"计划块"与"实际块"叠画（实际块虚线边框）（[Sunsama](https://www.sunsama.com/)）；Clockify 支持悬停事件直接开始计时或"复制为时间条目"。反面教训：Sunsama 移动端被投诉"计划时间不持久、重复任务被加进日历"（[测评](https://www.usecarly.com/blog/sunsama-review/)），回写必须带幂等键（entryId + 版本号）。

## 八、与时间统计整合

- **计划 vs 实际**：按块算偏差率，再按分类/技能汇总——这是技能卡片最有说服力的数据。
- **周复盘**：Sunsama 的 daily shutdown + weekly review 是范本：先看时间实际去哪了，再对照周目标，最后写一句复盘。
- **口径先定**：跨天块怎么切、会议算不算专注、暂停怎么扣，PRD 写死，否则报表永远对不上。

## 九、常见吐槽与设计陷阱

- **过度复杂**：功能堆叠让主路径变长；Motion/Reclaim 的自动排程要求每个任务都有时长与优先级，一旦不维护规则就退化成普通列表。
- **录入成本高**：Motion 中"没有时长的任务无法排程、没有截止或优先级的任务不会被排"（[测评](https://www.usecarly.com/blog/motion-ai-review/)）。对策是默认值、批量录入、从习惯一键生成块。
- **计划被反复挪动**：Motion 用户抱怨"计划一直在变，得盯着调度器"，工具反而增加心智负担。
- **同步冲突与幽灵条目**：Sunsama 移动端被投诉"重复任务被加进日历"（[测评](https://www.usecarly.com/blog/sunsama-review/)）；双向同步天然产生重复与覆盖。
- **移动端是短板**：Sunsama 手机端被评"近乎不可用"，且无离线模式——桌面优先的产品在手机上往往只剩"看"。

## 十、端差异与坑

| 坑 | 表现 | 处理 |
|---|---|---|
| 时区 | 出差后重复事件漂移 | 存 UTC + 原 TZID，按设备时区渲染 |
| 夏令时 | 02:30 事件春季不存在、秋季重复 | 按本地时间 + TZID 计算，不存在则顺延 |
| 同步冲突 | 两端改同一实例互相覆盖 | 字段级合并 + 序列号，冲突可见 |
| iCal 订阅 | 只读、刷新有延迟、无推送 | 不承诺实时，显示"上次同步" |
| 导出再导入 | 产生重复条目 | 必带 UID / SEQUENCE / DTSTAMP |
| 全天事件 | 部分工具日历直接不显示 | 单独泳道，明确语义 |

平台能力差异是硬约束：Things 只能读本机 Apple 日历、不能把待办写回、也不同步日历数据（[官方说明](https://culturedcode.com/things/support/articles/2803583/)）。"只读镜像"是低风险的正确姿势。

## 十一、功能分层

| 模块 | MVP | 完整版 |
|---|---|---|
| 视图 | 今日议程 + 周 | 日时间轴、月、多日、多日历 |
| 条目 | 统一 Entry、全天、跨天 | 参与者、地点、忙闲 |
| 重复 | L0 + 结束条件 + 单次跳过/改期 | L1/L2、THISANDFUTURE |
| 提醒 | 1–2 个、全天默认 09:00、错过汇总 | 多提醒、持续响铃、地点 |
| 习惯 | 时间窗柔性块 + 一键打卡 | 自动找位、冲突重排 |
| 计时 | 一键开始/结束回写 | 多段计时、番茄、中断恢复 |
| 统计 | 计划 vs 实际、周复盘 | 技能趋势、目标达成 |
| 互操作 | ICS 只读订阅（可选） | 双向同步、CalDAV |
| 协作 | 无 | 共享日历、预约页 |

## 十二、对我方产品的建议（含取舍）

**定位：日程表是"打卡与计时的容器"，不是第二增长曲线。** 用户是"想养成习惯的人"，不是"会议很多的高管"。

**做深**

1. **今日议程做主入口**：第一屏仍是打卡，下面是"今天的时间线"，习惯块、计划块、已完成计时混排。Sunsama/Structured 的共同点是"一个今天"，不是"一个完整日历"（[Structured](https://structured.app/)）。2. **习惯块 = 时间窗 + 时长 + 积分**：完成一次同时写打卡、计时、积分三处，绝不能要求"先建任务再打卡"。
3. **预估 vs 实际**：任何块可填预估分钟，计时结束落实际值，周报给"兑现率""超时最多"。技能卡片因此有硬数据。
4. **轻重复 + 单次例外**：只做 L0 与"跳过这次/改到明天"，底层仍存 RRULE 字符串，保证未来可导出 .ics。
5. **只读 ICS 订阅**：把 Google/Outlook 会议拉进来做冲突提示，不写回。Things 证明这已足够有用，且避开双向同步的冲突地狱。

**明确不做**

1. **双向日历同步、多日历管理**：OAuth 维护、增量同步、冲突合并的成本远高于收益。
2. **AI 自动排程**：Motion 差评集中在"计划被反复挪动、要人盯着"（[测评](https://www.usecarly.com/blog/motion-ai-review/)），与打卡产品需要的稳定感相斥。可做"建议时段"，不做全自动重排。
3. **月视图拖拽排期、共享日历**：频次低，稀释主线。
4. **完整 RRULE 编辑器**：BYSETPOS、THISANDFUTURE 用户看不懂，测试成本高。

**字段先留**（现在不做 UI）：`entry(id, kind, title, startAt, endAt, allDay, tzid, rrule, exdates, recurrenceId, dueAt, completedAt, estimateMin, actualMin, habitId, skillId, source, etag)`，V2 加同步无需迁移。

**验收指标**：建块耗时 < 5 秒；从块进入计时的比例；计划兑现率；周复盘打开率；因冲突提示改期的次数（验证提示是帮助而非噪音）。
