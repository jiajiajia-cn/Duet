# 竞品调研：同类产品怎么做的，我们该借鉴什么

> 配套文档：[PRD.md](./PRD.md) · 调研时间：2026-10 · 资料来源：官方产品页、帮助中心、App Store 评论、社区运营帖

## 0. 方法与边界

我们不是要做一个"更全"的产品，而是要回答三个问题：

1. 这四个模块（打卡 / 积分奖品 / 计时 / 技能）在成熟产品里分别被验证过什么？
2. 哪些设计是**共识**（可以直接抄），哪些是**取舍**（取决于我们的定位）？
3. 哪些是公认的**坑**（用户长期吐槽、开发者反复踩）？

## 1. 一张总览表

| 产品 | 它解决什么 | 它最强的地方 | 它不做 / 做得差 |
| --- | --- | --- | --- |
| **Habitica** | 习惯 RPG 化 | 任务四分类、组队、经济系统闭环 | 惩罚过重（掉装备/死亡）、学习成本高 |
| **Loop Habit** | 极简量化打卡 | 频率规则、统计、开源、离线 | 无激励、无社交 |
| **Streaks** | iOS 习惯链 | 手势交互、健康数据打通 | 上限 24 个习惯、无多人 |
| **小打卡 / 训练营** | 圈子打卡 | 圈子运营、排行榜、证书、付费营 | 重运营、轻数据 |
| **stickK** | 承诺契约 | 监督人（referee）+ 押金，约束力最强 | 真金白银，心理门槛极高 |
| **Forest** | 专注种树 | 专注即奖励、共同专注 | 不能暂停、单次 2h 封顶、榜单可刷 |
| **番茄ToDo** | 番茄 + 自习室 | 学霸模式、加入码自习室 | 忘了停导致虚高、自习室不显示实时时长 |
| **Focus To-Do / TickTick** | 任务 + 番茄 | 任务与专注联动 | 番茄入口深、口径不统一 |
| **StudyTogether** | 线上自习室 | 50/10 强同步、在场感 | 社交压力、时长延迟 15–30 分钟 |
| **Toggl / Clockify** | 时间追踪 | 项目归类、报表、时间线 | 无暂停（Toggl）、无激励 |
| **TimeBlocks** | 时间块记录 | 30 分钟粒度、记录极快 | 短任务记不准 |
| **My Rules / 攢攢** | 积分换奖励 | 自定义积分 → 自定义真实奖励 | 单人、无监督、无库存/审核 |

**空位**：把"打卡 + 计时"都当作积分来源、并且**用同一套审核/库存机制管理真实奖励**的产品，基本没有。这正是我们要站的位置。

## 2. 习惯打卡与监督打卡

### 2.1 Habitica：把习惯做成 RPG，但惩罚太重

- **任务分四类**：Habits（可正可负，可反复点）、Dailies（每天/每周固定，漏了扣血）、To-Dos（一次性）、Rewards（用金币买的自定义奖励）。这个四分法很值得抄——尤其 **Habits 支持"负向"** 和 **Rewards 是用户自定义**。
- **经济**：完成任务得金币 + 经验，金币可在 Rewards 里换自定义奖励（"看一集剧 10 金币"），宝石是付费货币。
- **组队**：Party 成员一起打 Boss，**有人漏做 Daily 全队掉血**——这是"互相监督"最狠的实现。Party 上限 30 人（**待接受的邀请也占名额**，这是个容易踩的坑）。
- **代价**：漏做 Daily 会掉血甚至"死亡"——掉 1 级 + 清空金币 + 掉 1 件装备（一瓶药水 25 金币回 15 HP）。对自律性弱的人是双重打击，容易直接卸载。
- **我们取什么**：任务四分类的"负向习惯"和"自定义奖励"；组队的"互相可见 + 团队加成"。
- **我们不取**：掉血/死亡/装备，惩罚只做"积分少拿"和"连续清零"，不制造二次挫败。

### 2.2 Loop Habit / Streaks：克制的记录派

- **频率规则是核心**：每天 / 每周指定几天 / 每周 N 次 / 每 N 天一次。这四种覆盖了 95% 的真实需求，再复杂用户就懒得设了（Loop 的 `frequency` 设计被大量开源项目照抄）。
- **Loop 的"分数"**用指数平滑，比"连续天数"更宽容；Streaks 则是硬连击，但允许"计划内跳过"。
- **一个容易漏的细节**：Loop 的 `goal_type` 分 `at_least`（至少完成 N）和 `at_most`（至多 N，如"每天最多喝 2 杯咖啡"）。**"至多"型当天永远不算"完成"**，只能用"是否破戒"来判定——这说明负向/上限型习惯需要独立的判定逻辑，不能复用正向打卡。
- 两者都证明：**打卡动作必须 1 次点击完成**，任何表单都是流失点。
- **我们取什么**：四种频率形态；"今日该做什么"由频率推导，而不是让用户自己筛。
- **我们不取**：只记录不给反馈（Loop 没有奖励，坚持全靠自觉）。

### 2.3 stickK / Beeminder：监督的本质是"有代价"

- stickK 的机制：立一个目标（如"每周去健身房 3 次"）→ 押一笔钱 → 指定一个 **referee（监督人）** 验证 → 失败则钱捐给"反慈善机构"。
- 结论：**监督有效的关键不是"被看见"，而是"失败有代价"**。只靠"朋友看一眼"的监督，三周后必然失效。
- **我们取什么**：监督人要有**实权**（确认/驳回打卡），且失败有**可感知的代价**（当日积分不发、连续中断、团队加成拿不到）。
- **我们不取**：真钱押金（合规与心理门槛），改用积分作为"内部货币"承担代价。

### 2.4 小打卡 / 训练营：圈子运营的土办法

- 圈子 + 打卡主题 + 排行榜 + 证书 + 补打卡卡券，付费训练营靠"押金返还"驱动。
- 运营靠人：社群打卡要靠群主每天催、发榜单、发红包。
- **补卡是有偿的**：小打卡把"补签卡"做成付费会员权益，且 1 个圈子每月限 4 次——说明"补卡必须有限制"是被市场验证过的结论，不是我们胆小。
- **我们取什么**：圈子、邀请制、催办、周报——把"群主手工做的事"产品化。
- **我们不取**：排行榜默认展示（小圈子攀比伤感情）、付费营模式。

### 2.5 日期边界：所有产品都要处理"凌晨算哪天"

- Streaks 的 `Start of Day` 默认 0:00，可设到 2:00（一天变成 02:00–次日 01:59）；Habitica 有 `Custom Day Start`。
- 结论：**"一天"的边界必须是用户配置项**，并且存 `local_date + tz_offset + day_start_hour`，**不能用服务器 UTC 日期**——否则夜猫子每天都会"丢一天"。

### 2.6 结论：我们的监督设计

| 行业做法 | 我们的做法 | 理由 |
| --- | --- | --- |
| 漏做扣血/死亡 | 只不发分 + 断连击 | 负反馈过重会劝退 |
| 押金/真钱 | 积分作为代价 | 免支付合规，仍然"疼" |
| 只"被看见" | 监督人有确认/驳回权 | 无实权的监督三周失效 |
| 全量公开 | 分级可见（是否完成公开，备注图片私有） | 隐私与体面 |
| 每日催 | 催办限频（每天每人每习惯 1 次） | 防骚扰 |
| 无限补卡 / 付费补签卡 | 默认关闭；开启后 T+2 窗口 + 每月 3 次 + 补卡不计"全勤" | 补卡是最大的作弊口子 |

## 3. 计时器与共同专注

### 3.1 状态机：只存时间戳，不靠前台 tick

全行业的正确写法只有一种：

```
remaining = planned - (now - startedAt - pausedTotal)
```

前台 tick 只负责渲染。关页面、切后台、杀进程、换设备，回来都用这条公式重算。Toggl 明确不做暂停（"暂停需要服务端持续监控，性能不划算"），Clockify 反过来做"锁屏自动停、解锁自动开"——两种取舍，我们选**服务端权威 + 心跳**的中间路线。

### 3.2 放弃与失败的三种流派

| 流派 | 代表 | 做法 | 体感 |
| --- | --- | --- | --- |
| 强惩罚 | Forest | 树枯死，奖励归零，枯树永久留痕 | 仪式感强，但"看一眼剩余时间树就枯了"被大量吐槽 |
| 极强惩罚 | Virtual Cottage | 除退出游戏外无法停止 | 极端，劝退 |
| 部分计入 | Focusmo | 提前停止按已进行时长计入当日目标 | 温和，但激励弱 |

**我们的做法**：三档严格度（宽松/标准/严格）由用户选，默认标准（记时长、不给分、不算连续）。把"要不要逼自己"的选择权交出去，而不是替用户决定。

### 3.3 共同专注：先弱同步，再强同步

| 模型 | 代表 | 机制 | 问题 |
| --- | --- | --- | --- |
| 弱同步 | 番茄ToDo 自习室 | 各自计时，房间只显示在场与今日时长 | **时长要等本轮结束才更新**，房主无法判断谁在真专注 |
| 强同步 | Forest Together / StudyTogether | 同一套起止时间，到点一起响 | 对延迟、断线、作息差异极敏感 |
| 随时加入 | StudyTogether | 轮次中途可进 | 需要严格的主持人 |

**我们的做法**：默认弱同步（成本低、不怕作息差），提供"统一起止"开关；成员**已进行时长实时显示**（直接用 `now - startedAt`），这是番茄ToDo 最明确的可差异化点。

### 3.4 报表：固定的五件套

今日/本周/本月汇总 → 项目（技能）饼图与柱图 → 每日目标与连续 → 时间线（15 分钟一格，可一键补空档）→ CSV 导出。

时间线比"多一张图表"更有价值：它把"忘记记录"变成了"顺手补记"。

### 3.5 已知的坑

- **忘了停**导致 8 小时假数据（番茄ToDo 最大吐槽）→ 暂停超时提醒 + 单次/单日上限。
- **榜单可刷**（Forest 用户评论）→ 单账号单活跃会话 + 会话重叠检测 + 服务端重算。
- **休息计入时长**导致数据虚高 → 休息永远不进专注统计。
- **番茄只能 5 分钟倍数**（番茄ToDo）→ 我们给 1 分钟粒度。
- **iOS 无法屏蔽 App** → 不做"学霸模式"的承诺，只做提醒与沉浸视图。

## 4. 积分与奖品兑换

### 4.1 经济系统的三条铁律

1. **只增不改的账本**：余额永远由流水推导（或冗余 + 每日对账），改余额必须新增冲正流水。否则一个月后你无法解释"为什么我少了 200 分"。
2. **发放有上限**：Habitica 靠"任务越难给得越多 + 每日结算"控制节奏；纯自定义系统必须有每日上限与单次上限，否则用户会把"喝水"拆成 20 条。
3. **sink 与 source 平衡**：奖品定价要参考"圈子总发放 vs 总消耗"。一个只有 source 没有 sink 的积分系统，三个月就通胀到没有意义。

### 4.2 兑换订单状态机（行业通用形态）

```
待审核 ──通过──► 待发放 ──发货──► 已发放 ──确认──► 已完成
   │                │                 │
   ├──驳回──► 已拒绝 ─► 已退款         └──售后──► 已退款
   ├──取消──► 已取消 ─► 已退款
   └──超时/下架──► 已关闭
                    └─发货失败──► FAILED（可重试，不重复扣分）
```

关键点：
- **扣分时机有两种**：① 下单即扣（冻结），驳回退；② 下单冻结、履约时实扣。对小系统，**① 更简单**（少一个 `frozen` 维度的对账），代价是驳回必须保证退款成功——所以退款要放在同一个事务里。
- **快照**：兑换单必须存商品快照（标题/图/价格/履约方式），否则改价会污染历史记录。
- **库存与积分在同一个事务**：`UPDATE reward SET stock = stock - 1 WHERE id = ? AND stock >= 1`，影响行数为 0 就失败。**禁止"先查再改"**。
- **幂等键**：同一个"确认兑换"按钮被连点两次，只能产生一张单（前端置灰不够，服务端必须去重）。
- **已履约的物品不能自动退款**，只能管理员手动调整并留痕。

### 4.3 重复兑换与归档

- 限兑要分三层：**总限兑**（每人终身 N 次）+ **周期限兑**（每月 N 次）+ **冷却期**（N 天），用一个 `reward_user_quota` 原子占额表实现。取消/拒绝时释放名额，已发放不释放。
- **归档 ≠ 删除**：归档后从商城消失、不可兑换、**已产生的订单继续履约**，历史记录与快照完整保留。
- 有兑换记录的奖品**禁止硬删除**，否则订单会变成孤儿数据；硬删除只允许用于"从未被兑换过的草稿"。
- 库存无限（`null`）要单独表达，不要用 `999999` 糊弄。

### 4.4 积分账本该有哪些字段

```
id, account_id, biz_type, biz_id, idempotency_key,
delta, balance_before, balance_after,
operator_id, reason, reversal_of, expires_at, created_at
```

- **只追加**，退款/冲正用反向分录（`reversal_of` 指向原流水），永不 UPDATE 或 DELETE。
- `balance_before/after` 是为了对账时能定位"从哪一条开始错的"。
- `idempotency_key` 防重复提交（前端网络重试是常态）。
- 每日跑一次 `sum(delta) == balance` 的对账，不一致就告警。

### 4.5 防通胀与防刷的组合拳

| 手段 | 防什么 |
| --- | --- |
| 打卡时间窗 | 集中补卡 |
| 补打卡默认 0 分 + 月上限 | 月末突击 |
| 审核（举证/见证） | 虚假打卡 |
| 计时服务端结算 + 单日上限 | 挂机刷时长 |
| 每日获取上限 | 刷分总量 |
| 库存/定价/限兑 | 通胀与挤兑 |
| 流水透明（成员可见） | 管理员滥用 |

**要不要监控通胀**：电商会员体系会盯三个数——发放/消耗比、积分通胀率（建议 < 10%）、沉默积分占比（建议 < 30%）。我们只在管理后台放一个简单的"总发放 / 总消耗 / 当前结余 / 人均结余"，够判断"是不是发太多了"。

**哪些手段对我们是过度设计**：设备指纹、IP 风控、T+7 延迟到账、实名校验、反作弊追回——这些是日活百万的产品才需要的。5–50 人的圈子，**圈子本身就是一个强信任边界**，真正的风险是"手滑"和"忘了审核"，不是黑产。

## 5. 日程表

核心结论：**日程表是打卡与计时的容器，不是第二增长曲线**。

- **事件与待办统一建模**（一张表 + `kind`），不做两套日历两套提醒。
- **习惯进日历用"时间窗柔性块"**（07:00–09:00 之间完成 30 分钟），不用"07:00 必须开始"的硬事件——硬事件错过就挫败。
- **预估 vs 实际**是技能卡片最有说服力的数据来源，也是日程表存在的理由。
- 只做 **L0 重复规则**（每天/每周几/工作日/每月同日/每 N 天 + 结束条件），例外只做"跳过这次/只改这次"。
- 提醒给三档（准时/提前 10 分钟/提前 1 小时），别给 0–10080 分钟的输入框；全天事件默认当天 09:00。
- **不做**：AI 自动排程（Motion 的差评集中在"计划被反复挪动"）、双向日历同步（OAuth + 增量同步 + 冲突合并的成本远超收益）、共享日历。
- 可选：**只读 ICS 订阅**（把 Google/Outlook 的会议拉进来做冲突提示），成本低、避开了写回的坑。

## 6. 八条横向结论（会直接影响 PRD）

1. **动作要轻**：打卡 1 次点击、建日程 5 秒、计时 1 次点击。任何超过 2 步的主路径都会流失。
2. **奖励要真**：虚拟徽章很快失效，真实奖励（一杯奶茶、一场电影）才有牵引力。这是 My Rules / 攢攢 的核心洞察。
3. **惩罚要轻**：负反馈过重会让人卸载。用"少拿"代替"扣分"。
4. **数据要可信**：计时靠服务端，打卡靠审核，账本靠流水。可信度一旦崩，整个系统就没意义。
5. **配置要少**：默认值能覆盖 80% 场景，高级配置折叠起来。
6. **可见性要分级**：完成状态可以公开，备注和图片默认私有。
7. **提醒要克制**：默认 1 条提醒 + 1 条错过提醒，多了就是骚扰。
8. **承认限制**：iOS 推送要装到主屏幕、浏览器不能屏蔽 App、PWA 不能常驻后台——这些在需求里就写清楚，别承诺做不到的事。
